UIUC Course Explorer — Architecture & Data Flow

How the data is stored, how a question travels through the app, and how the hybrid SQL + vector RAG answer engine works. Companion to DECISIONS.md (the why) and DEPLOYMENT.md (the ops).

1. Two storage layers

Everything is one database — SQLite locally (data/courses.db), Neon Postgres in production, selected by whether DATABASE_URL is set. app/db.py hides the difference so every query is written once.

Layer 1 · exact facts

Relational tables

Plain SQL tables, ordinary TEXT/INTEGER columns. Rows are upserted on their natural key, so re-scraping is idempotent. Queried by the agent's sql_db_query tool for structured questions — instructors, CRNs, counts, credit hours, gen-eds, grades.

Layer 2 · meaning search

Vector store (course_embeddings)

Postgres-only, via the pgvector extension. Each course's catalogue description is turned into a 384-number vector — its position in "meaning space." Queried by course_content_search for open-ended "what covers X" questions.

Vector store

CREATE EXTENSION vector;

CREATE TABLE course_embeddings (
    subject        TEXT,
    course_number  TEXT,
    description     TEXT,            -- the raw blurb, kept for display
    embedding      VECTOR(384),      -- 384 floats from bge-small-en-v1.5
    updated_at     TIMESTAMP,
    PRIMARY KEY (subject, course_number)   -- one row per COURSE
);
CREATE INDEX … USING hnsw (embedding vector_cosine_ops);

The embedding is the description run through BAAI/bge-small-en-v1.5 (via fastembed / ONNX, local CPU, no API key, no rate limit). The HNSW index makes nearest-neighbour search fast instead of a full scan. Rows are written at scrape time (save_course_embedding) or in bulk by app/backfill_embeddings.py.

3. How data gets in

UIUC's firewall blocks datacentre IPs, so scraping only works from a residential machine. Render never scrapes — it only reads Neon.

  1. 1Scrape locally — app/scraper.py pulls the Course Explorer XML from your machine into sections + meetings, and embeds each new description into course_embeddings as it goes.
    CSV loaders (load_grades.py, load_tre.py, load_geneds.py) fill the other three tables from wadefagen/datasets.
  2. 2Push to Neon — the same scripts write straight to Postgres when DATABASE_URL points at Neon. The initial load was a one-off SQLite→Neon migration (migrate_sqlite_to_neon.py); after that, app/sync_requests.py --run DEPT refreshes a department on demand.
  3. 3Backfill vectors — app/backfill_embeddings.py fills any course_embeddings gaps (drops & rebuilds the HNSW index around the load).
  4. 4Render reads — the FastAPI app (app/api.py) connects to the same Neon database, read-only in practice, and serves the UI + /ask.

4. How a question is answered

  1. 1Browser → POST /ask/stream — sends { question, history }, where history is the last 3 turns from the on-page transcript (nothing is stored server-side).
  2. 2Pre-LLM guardrails — length cap, a shared daily cap, and a per-IP rate limit run before anything is spent. Blocked → a plain JSON error, no stream. Every attempt is written to ask_log.
  3. 3Build the agent input — the trimmed history is prepended to the question as "context only, do not re-answer," so follow-ups like "who teaches it?" resolve.
  4. 4The agent picks a tool — a LangChain tool-calling agent on Groq openai/gpt-oss-120b. It chooses one of two tools per question:

    sql_db_query

    Structured facts: "who teaches CS 225", section counts, CRNs, credit hours, gen-eds, grade trends.

    Writes real SQL against the five relational tables and runs it. A named course's description is read straight from sections.description here — more precise than a similarity search.

    course_content_search  (the RAG path)

    Open-ended: "what courses cover machine learning", "classes about the brain."

    Runs the multi-query vector retrieval in section 5, then hands the matched descriptions back to the agent as context.

  5. 5Generate & stream — the agent writes the answer from the tool's result and streams it back token-by-token as Server-Sent Events (status → token → done). The final answer is classified and logged to ask_log.

5. The RAG loop, in detail

This is what course_content_search does between steps 4 and 5 above. It is Retrieve → Augment → Generate: pull the most relevant descriptions, put them in the LLM's context, let it write the answer.

  1. 1Expand the query — one small non-streaming LLM call rewrites the topic and adds 3 distinct facets. "machine learning" → ["machine learning", "supervised learning", "unsupervised learning", "ethical AI and bias"]. Falls back to the raw topic on any failure. Toggle with RAG_MULTIQUERY.
  2. 2Embed all four locally — the same bge-small model that built the table, one batch call. (Must be the same model, or the vectors aren't comparable.)
  3. 3Search pgvector per phrase — SELECT … embedding <=> $vec AS distance ORDER BY distance LIMIT 6. <=> is pgvector's cosine-distance operator, served by the HNSW index. Smaller distance = closer meaning.
  4. 4Reciprocal Rank Fusion — merge the four result lists: score += 1 / (60 + rank), keyed on (subject, course_number), keeping the best distance seen. Take the top 10.
  5. 5Return as context — the merged course descriptions are returned to the agent as text; it groups them into a thematic overview rather than a flat list.
Structured questions never enter this loop — they never call the tool, so they pay nothing for the expansion call. Only the semantic path does.

6. Conversation memory

The server is stateless. The browser keeps chatHistory (last 10 turns), sends the last 3 with each question, and the server re-trims them (question ≤ 200 chars, each prior answer ≤ 250) before prepending them as context. A "New chat" button or a page reload clears it — nothing is persisted, so there is no session store to manage.
