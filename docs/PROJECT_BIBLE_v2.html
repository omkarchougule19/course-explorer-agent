1. What this is

Illini Course Copilot is a dataset-and-agent project built on UIUC's public Course Explorer data. Not affiliated with, endorsed by, or sponsored by the University of Illinois. It:

  1. 1Collects course, section, instructor, meeting and enrollment-status data from UIUC's public XML, plus supplementary public datasets (grade distributions, "Teachers Ranked as Excellent", Gen Ed categories), the registrar's academic calendar, and prerequisites parsed from course descriptions.
  2. 2Structures it into a documented schema that runs unchanged on SQLite (local development) and Postgres / Neon (production).
  3. 3Serves it through a FastAPI backend and an 8-page browser site: browse and filter sections, departments, the academic calendar, a schedule builder, instructor pages, data freshness.
  4. 4Answers plain-English questions through a LangChain agent that writes its own read-only SQL for structured questions and runs pgvector semantic search for content questions, streaming a sourced answer.

Why it exists

It is a work sample for AI Engineer / Forward-Deployed Engineer roles. It walks the whole applied-data loop — pull from an external source, structure it, expose it through an API, let a non-technical user ask in plain language — and keeps going into the parts usually skipped: retrieval quality, guardrails, security, feedback loops, and a measured evaluation of the agent itself.

2. Operating model and guiding principles

These constraints shaped nearly every technical decision.

  • Free forever. Render free web service + Neon free Postgres; no paid tier, no standing cost. The instance sleeps when idle, and that trade-off is accepted.
  • Scraping runs locally, never in the cloud. UIUC's firewall rejects datacenter IPs and soft-blocks long sweeps, so the operator scrapes from a residential IP and writes straight to Neon.
  • Demand-driven freshness. No scheduled re-scrape: visitors request a department refresh, and the operator processes the queue by hand.
  • One query text, two backends. Every SQL string is written once; app/db.py translates. Nobody needs Postgres to develop.
  • Low traffic, simple over scalable. One worker, no cache layer, no job queue.
  • Self-hosted embeddings. fastembed runs bge-small-en-v1.5 locally in both the scraper and the web app; no embeddings API.
  • Defence in depth for the LLM. The prompt is one layer, never the only one: model-written SQL is parsed, allowlisted and run read-only on a restricted role, and the budget is protected by limits that run before any model call.
  • Measure, don't assume. Prompt and pipeline changes are judged on the eval set against the live database.
Each of these has its reasoning and rejected alternatives in DECISIONS_v2.md (by topic); the dated v1 history is in git (git show bbf824e:DECISIONS.md).

5. Data model

All tables live in one database; db.py maps the few DDL keywords that differ per backend. Counts are production on 2026-09-24.

7. Request flows

POST /ask/stream (and /ask)

Body limit → concurrency ceiling → length cap → a pending slot in ask_log → shared and per-IP caps counted in reservation order → the agent (one of two tools, with SQL through the guard and the read-only role) → a streamed, cited answer → the slot rewritten with the outcome. The full, illustrated path is in architecture_v2.html, sections 4-6.

Plain reads

GET /sections, /subjects, /courses/{subject}, /stats, /freshness, /meetings, /calendar, and the course detail routes (…/grade-trend, …/prereqs) are bounded, parameterised reads straight from the catalog — no LLM. Browse filters (level, and the schedule chips) run in Python after the SQL fetch because course numbers and times are text. POST /schedule/conflicts checks day and time overlaps for 2-50 CRNs.

POST /sync/request → GET /sync/status

A visitor on a stale department presses Sync; the counter goes up. The operator reads --list (or /sync/status) and refreshes the most-requested departments locally.

Feedback and admin

POST /ask/feedback and POST /feedback never fail loudly (a storage error returns {"ok": false}); both are capped. /admin/* needs the X-Admin-Token header.

8. The agent in detail (agent.py)

  • Provider by key: GROQ_API_KEY, then OPENAI_API_KEY, then GEMINI_API_KEY; LLM_PROVIDER forces one. Production: Groq openai/gpt-oss-120b, with one retry on qwen/qwen3.8-27b after a rate limit (before any answer text is streamed).
  • Budget: Groq's free tier caps about 200K tokens per day per model and 8,000 per minute, shared by production, development and evals. The prompt (~2,200 tokens) is re-sent every step, so steps are capped at 6 and any tool result at 6,000 characters.
  • The prompt is organized as scope, how to query, tables, how to answer, and live DATA NOTES; it has fixed sentences for refusals and missing data so both are recognizable. It scored 89.7% answer-OK on 29 questions against the live database (62.1% for the previous version).
  • SQL access is sandboxed by the guard and the role (section 11), not just by the prompt.
  • Semantic search is multi-query expansion + Reciprocal Rank Fusion inside the tool, so structured questions never pay for it. Tunable with RAG_MULTIQUERY, RAG_SUBQUERIES, RAG_K_PER, RAG_K_RETURN.
  • History is windowed and stateless: the last 3 turns, re-trimmed, context only.
  • Citations are deterministic, parsed from the executed SQL; no extra model call.
  • Quality is checked by the eval harness and the course-agent-qa subagent; abuse by course-app-redteam.

10. Operations / runbook

  • Refresh departments: locally, python -m app.sync_requests --list, then --run DEPT … or --run --top N, with DATABASE_URL pointing at Neon. Stop when wall detection reports the firewall; retry after a cooldown.
  • Full scrape of a term: python -m app.scraper --year YYYY --semester SEASON [--subjects …]. Lower --concurrency and raise --section-delay if requests start failing. Cloud runners don't help (same firewall).
  • Rolling the term: edit CURRENT_YEAR / CURRENT_SEMESTER in app/terms.py, then re-run the loaders. The prompt's DATA NOTES follow the data automatically.
  • After a bulk load or a model change: python -m app.backfill_embeddings.
  • Load a term's calendar: python -m app.load_calendar --term 2026-fall --url ….
  • Deploy: merge to master, push, then Manual Deploy in the Render dashboard; check the live site.
  • Before shipping a prompt or agent change: run the offline tests, then python -m evals.run --arms prod --db env --provider openai -y (full runs on OpenAI so Groq's shared daily budget stays with users), twice for a comparison, then a few targeted questions on Groq.
  • After touching the API, guardrails or logging: run course-app-redteam (writes security_findings.md). When cold starts feel slow: run startup-critic.

11. Security posture

  • Model-written SQL, three layers: the prompt; sql_guard.py (one read-only query over the catalog tables, parsed with sqlglot, run in a READ ONLY transaction with an 8 s timeout); and the SELECT-only app_ro role.
  • Headers on every response: CSP with script-src 'self' (no inline scripts), frame-ancestors 'none', X-Frame-Options: DENY, HSTS, nosniff, no-referrer.
  • Abuse limits before any model call: size, length, concurrency, shared and per-IP caps with reserved slots; feedback caps; bounded public inputs.
  • No internal detail in responses: driver, connection and agent errors are logged server-side only.
  • Admin via X-Admin-Token only, constant-time compare, always 403 on failure. API docs off unless ENABLE_DOCS.
  • Output encoding on every database value; the Markdown renderer only links same-site paths or https:// URLs.
  • Dependencies hash-pinned and audited (pip-audit: no known vulnerabilities, 2026-09-24).
  • Accepted: the per-IP key uses a spoofable header (the shared cap is the real control). Red-team history: security_findings.md.

12. Conventions

  • One query text, both backends. Write ? placeholders; never branch on backend outside db.py; use db.upsert().
  • Values: semester and term lowercase; subject codes uppercase; a term is always (semester, year); course_number is text.
  • Run scripts as modules from the project root (python -m app.…).
  • No inline scripts or handlers in static/; every page's code lives in its -page.js file (an offline test enforces it).
  • Visitor-facing copy stays short and never names env vars, providers, keys or repo files.
  • Decisions get logged as they happen: the current state in DECISIONS_v2.md, remaining work in implementation_plan_v2.md, in the same commit as the change.
  • Commits on a branch, merged when approved; nothing ships until a manual deploy.
  • No new standing cost, provider or paid tier without a logged decision.

13. Known limitations

  • Cold starts: the free instance sleeps; the first visit waits for Render plus about 2 s of app startup.
  • Groq's free per-minute token limit makes multi-step questions and simultaneous users slow (4-56 s observed).
  • Grades and instructor rankings are empty until upstream publishes terms in the window.
  • Fall 2026 is synced for 84 of 191 subjects.
  • Fall 2026 enrollment status is only a scheduling code; no term has seat counts.
  • Cross-listed courses are separate rows per subject; the ranking join is name-based; gen-eds are a single snapshot.
  • Vector search needs Postgres; local SQLite has no RAG tool.

15. Glossary

  • CRN — Course Reference Number, unique per section per term.
  • Catalog tables — the seven relational tables the assistant may query.
  • DATA NOTES — the live facts appended to the prompt at startup (current year, terms, unpublished registration, empty tables).
  • SQL guard — app/sql_guard.py, the parse-and-allowlist check on model-written SQL.
  • Reserved slot — the pending row a question writes to ask_log before the model runs, so rate limits hold under concurrency.
  • Detailed / fast mode — the scraper with or without the per-section and per-course requests.
  • Hybrid agent — the SQL toolkit plus the pgvector RAG tool, chosen per question.
  • Multi-query expansion / RRF — rewriting a topic into facets before vector search, then merging the ranked lists by Reciprocal Rank Fusion.
  • Demand-driven refresh — visitors request department syncs; the operator runs them locally.
  • Wall — the point where UIUC's firewall starts returning empty lists; sync runs stop there.
  • Active term window — current term ± 2 on the spring / summer / fall cycle (terms.py).
  • TRE — "Teachers Ranked as Excellent", a published UIUC list.
