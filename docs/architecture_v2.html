Illini Course Copilot — Architecture & Data Flow

How the data is stored, how it gets in, how a question travels through the app, how model-written SQL is kept safe, and how the hybrid SQL + vector RAG answer engine works. Version 2, written from the code as of 2026-09-24. Companion to DECISIONS_v2.md (the why) and DEPLOYMENT_v2.md (the ops).

1. Three kinds of storage, one database

Everything lives in one database: SQLite locally (data/courses.db), Neon Postgres in production, chosen by whether DATABASE_URL is set. app/db.py hides the difference, so every query is written once with ? placeholders.

Layer 1 · exact facts

The catalog

Seven relational tables. Rows are upserted on their natural key, so re-scraping is idempotent. The only tables the assistant's SQL may touch, through the SQL guard and a SELECT-only role.

Layer 2 · meaning search

Vector store (course_embeddings)

Postgres only, via pgvector. Each course's description as a 384-number vector. Reached only through the course_content_search tool, never through SQL.

A third group, invisible to the assistant: the app's own bookkeeping — ask_log (every question, its outcome and latency), answer_feedback, site_feedback and sync_requests. They hold other users' IPs and questions, so the SQL guard and the database role both exclude them.

Vector store

CREATE EXTENSION vector;

CREATE TABLE course_embeddings (
    subject        TEXT,
    course_number  TEXT,
    description    TEXT,             -- the raw blurb, kept for display
    embedding      VECTOR(384),      -- from BAAI/bge-small-en-v1.5
    updated_at     TIMESTAMP,
    PRIMARY KEY (subject, course_number)   -- one row per COURSE
);
CREATE INDEX … USING hnsw (embedding vector_cosine_ops);

The embedding is the description run through bge-small-en-v1.5 via fastembed (ONNX, local CPU, no key, no rate limit). The HNSW index makes nearest-neighbour search fast. Rows are written at scrape time or in bulk by app/backfill_embeddings.py. 5,464 rows in production.

3. How data gets in

UIUC's firewall rejects datacenter IPs and soft-blocks long sweeps (it answers with empty lists instead of an error), so scraping only happens from the operator's residential machine. Render never scrapes; it only reads Neon.

  1. 1A visitor asks for fresher data — pressing Sync on a stale department sends POST /sync/request, which increments that department's counter in sync_requests.
    No scheduled full re-scrape exists; demand decides what gets refreshed.
  2. 2The operator refreshes locally — python -m app.sync_requests --list ranks departments by demand; --run DEPT … (or --run --top N) scrapes the current term, plus the next if UIUC has published it, and writes straight to Neon.
    Wall detection stops the run after 2 departments in a row come back empty or have their term probe rejected. Departments synced in the last 7 days are skipped.
  3. 3The other tables — load_grades.py, load_tre.py and load_geneds.py read wadefagen/datasets CSVs (grades and rankings kept to a rolling term window from terms.py); load_prereqs.py parses prerequisites out of descriptions; load_calendar.py parses the registrar's page for a term.
  4. 4Vectors — the scraper embeds new descriptions as it goes; backfill_embeddings.py fills any gaps (dropping and rebuilding the HNSW index around a bulk load).
  5. 5Render reads — app/api.py serves the pages and the API from Neon. Model-written SQL uses a separate, SELECT-only connection (section 5).
    Production was first populated by copying a complete local SQLite database into Neon (migrate_sqlite_to_neon.py), because a cloud-bound full scrape hit the soft block.

4. How a question is answered

  1. 1Browser → POST /ask/stream — sends { question, history }. The chat is kept in the tab's sessionStorage; history is its last 3 turns.
  2. 2Cheap refusals first — a body over 256 KB gets 413; if the concurrency ceiling is full (2 in production) the request gets an immediate 503 "busy".
  3. 3Guardrails, with a reserved slot — a question over 500 characters is rejected; otherwise a pending row is written to ask_log before any model call, and the shared daily cap (250) and per-IP limits (10/hour, 60/day) are checked by counting rows in reservation order. Parallel requests therefore can't all slip past on one count. Blocked → a plain JSON error, no stream.
  4. 4Build the agent input — the trimmed history (question ≤ 200 chars, answer ≤ 250) is prepended as "context only, do not re-answer". The system prompt carries the schema, the house rules and live DATA NOTES (current year, terms in the data, which terms have unpublished registration, which tables are empty).
  5. 5The agent picks a tool — a LangChain tool-calling agent on Groq openai/gpt-oss-120b (one retry on qwen/qwen3.8-27b after a rate limit). One of two tools per question:

    sql_db_query

    Structured facts: who teaches CS 225, section counts, meeting times, gen-eds, prerequisites, deadlines.

    The written SQL passes the SQL guard, then runs in a read-only transaction on the SELECT-only role (section 5). A result over 6,000 characters is cut, with a note to narrow the query.

    course_content_search  (the RAG path)

    Open-ended: "what courses cover machine learning", "classes about the brain".

    Runs the multi-query vector retrieval in section 6 and hands the matched descriptions back as context.

  6. 6Generate, cite and stream — the answer streams back as Server-Sent Events (status → token → done). If it answered, a footer names the datasets the executed SQL touched and each subject's last sync. The reserved ask_log row is rewritten to the real outcome and latency, and the concurrency slot is released.

5. Keeping model-written SQL safe

Three independent layers. None relies on another, so one misconfiguration doesn't reopen the database.

  1. 1The prompt — stays in scope, refuses role changes, treats tool results as data, never instructions.
  2. 2The SQL guard (app/sql_guard.py) — parses the statement with sqlglot. Allowed: exactly one query with a SELECT (or set-operation) root, no write, DDL or session node anywhere in the tree, only the seven catalog tables, none of a small denylist of functions (pg_sleep, set_config, query_to_xml, file functions). Anything else is returned to the model as an error it can fix.
    Catches what prefix checks miss, e.g. WITH d AS (DELETE … RETURNING *) SELECT ….
  3. 3The database — every statement runs in a READ ONLY transaction with an 8 s statement_timeout (transaction-scoped, so it holds through Neon's pooler), connected as app_ro: SELECT on the seven catalog tables only. On Render, the assistant refuses to answer if that role isn't configured.

6. The RAG loop, in detail

What course_content_search does inside step 5 above: Retrieve → Augment → Generate.

  1. 1Expand the query — one small non-streaming LLM call rewrites the topic and adds 3 distinct facets. "machine learning" → ["machine learning", "supervised learning", "unsupervised learning", "ethical AI and bias"]. Falls back to the raw topic on any failure. Toggle with RAG_MULTIQUERY; its tokens are never streamed to the user.
  2. 2Embed locally — the same bge-small model that built the table, one batch call.
  3. 3Search pgvector per phrase — ORDER BY embedding <=> $vec LIMIT 6. <=> is cosine distance, served by the HNSW index.
  4. 4Reciprocal Rank Fusion — merge the lists: score += 1 / (60 + rank), keyed on (subject, course_number), keeping the best distance. Top 10.
  5. 5Return as context — the agent groups the merged descriptions into a thematic overview.
Structured questions never enter this loop, so they never pay for the expansion call. On local SQLite the tool isn't registered at all.

7. Conversation memory

The server is stateless. The browser keeps the chat in sessionStorage (the last 10 turns, each answer capped at 8,000 characters), so it survives moving between pages and reloading, and clears when the tab closes or with New chat. Each question sends the last 3 turns; the server re-trims them and uses them only to resolve references like "it" or "the second one". Nothing about the conversation is stored on the server beyond the question log.
